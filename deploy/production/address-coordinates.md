# 用户地址选点与骑手导航

本方案不提供后台楼栋管理，也不需要后台浏览器地图 Key。用户在「新增/编辑收餐地址」点击「在地图中设置位置」，通过微信原生地图选点，将 GCJ-02 经纬度随地址保存。

## 发布

1. 先发布 user-api。Flyway 自动执行 V8__address_coordinates.sql，为 user_address 增加 latitude、longitude，为 user_order_detail 增加 destination_latitude、destination_longitude。请勿修改旧迁移或手工将迁移标记为已完成。
2. 再发布 rider-api，使骑手导航读取订单目的地坐标快照。
3. 更新用户端与骑手端小程序。用户端已声明 chooseLocation 和 scope.userLocation；在微信公众平台确认位置接口权限及隐私保护指引已按实际用途配置，将地址位置用于订单配送。使用真机验证授权、选点和导航。
4. 发布后旧版用户端无法提交缺少坐标的新增/编辑地址，也无法使用缺少坐标的旧地址创建新订单，应提示用户更新小程序并补充位置。

## 行为

- 地图选点成功后保留精确坐标；用户更换楼栋文字后，须重新选点。只修改门牌不清除楼栋入口位置。
- 取消地图选点不会清除原位置；拒绝位置授权时提供设置入口。
- 后端验证坐标完整性及范围，不能仅绕过前端提交文字地址。
- 下单时从当前用户拥有的地址读取坐标并复制到订单。后续修改地址不覆盖该订单已保存的目的地。
- 对历史缺少坐标的未结束订单，编辑原地址时，仅补齐用户、地址编号、楼栋和门牌完全相符的订单；不覆盖已有坐标，不补齐已完成/已关闭订单。
- 如旧订单关联地址已删除或楼栋/门牌已变更，不猜测该订单目的地，继续使用文字地址配送。
- 历史订单仍缺少坐标时，请用户编辑原收餐地址，保持楼栋/门牌不变，选择准确位置并保存；骑手刷新导航页后读取补齐的坐标。

相关接口：POST /api/user/v1/addresses 与 PUT /api/user/v1/addresses/{id} 接收 latitude、longitude；GET /api/user/v1/addresses 同时返回这些字段。未提供或无效时返回 400。

验证已覆盖地址校验、订单坐标快照、骑手读取、前端选点/取消/拒绝授权，以及临时 MySQL 中迁移约束和历史订单补齐边界。原生地图授权及导航仍需微信真机联调。
